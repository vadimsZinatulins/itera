# Durable conversations

Ticket 06 adds ordinary goals/organisation chat and explicitly requested authoring assistance. Ticket 07 adds opt-in approved-source practice, explanations and hints in the same conversation. Ticket 09 adds incremental, learner-reviewed Practice recaps. Ticket 10 adds adaptive assessments in the same chat. Suggested threads remain a later ticket. Reference notes, profile, Drafts and other Subjects are never retrieved for this workflow.

## Persistence and authorisation

With local Supabase running, run `bash scripts/migrate.sh` to apply pending migrations, including `supabase/migrations/202603010006_conversations.sql`, without resetting data. For a deliberate fresh local database, stop the app and use `bash scripts/migrate.sh --force` (deletes accounts/content/keys after typed confirmation). See [migration runner details](authentication.md#local-migration-runner). `GET /api/conversations?subject=<uuid>` lists the current account's trail; adding `conversation=<uuid>` reads its ordered turns. `POST /api/conversations` accepts only `{ subject, conversation, operation, text, practice?, assessmentRevision? }` with stable UUID identities. The server never trusts a supplied account, history, assistant message, model or source selection.

The authenticated `send_conversation_message` RPC checks the live session and Subject ownership, serialises each conversation, and atomically inserts the conversation on its first message plus its user turn and incomplete reply record. Tables are read-only to account JWTs, with active-session RLS. The service-only reply RPC updates an existing owned turn; it cannot create missing conversations or resurrect deleted Subjects. Subject/account cascades remove history.

Replaying the same operation with identical text returns its saved identity without contacting OpenAI. Reusing it with different content/scope is rejected. Concurrent new sends while a reply is pending are rejected; a pending lease expires after 90 seconds if the server dies. History is always marked **incomplete** until the final completed result is successfully persisted. Browser retries preserve the operation in the mounted session. Device-only unsent recovery and explicit generation-retry UX belong to ticket 08; there is intentionally no automatic generation retry.

## Streaming and limits

`lib/openai/server.ts` owns credential access. One user-initiated Responses API request uses the currently saved supported model/key, `store:false`, `stream:true`, and `max_output_tokens:2048`. No provider conversation or previous-response identifier is used. With practice off (the default), only this conversation's ordered messages and fixed source-free instructions leave the app. With practice on, the server additionally supplies current approved snapshots and learner-reviewed provisional observations in this Subject, with fixed practice instructions; source text cannot change access rules. No tools or provider-side retrieval are enabled. Earlier partial replies are identified as incomplete in subsequent context. No hidden summaries or whole-account reprocessing.

The route emits newline-delimited JSON: a persisted `saved` event, text `delta` events, then `status:complete|incomplete`. Completion is sent only after persistence. Partial output is checkpointed at most every 500 ms and once on termination; an abrupt process loss may lose the last uncheckpointed fragment, never convert it to complete. Provider EOF, incomplete/failed events, transport interruption and limits leave incomplete outcomes. Persistence failures are disclosed without claiming saved completion.

Bounds: 12 KB request envelope, 8,000 UTF-8 bytes per message, 100 turns and 28,000 bytes of existing history plus new input at admission, a further 36 KB encoded provider-input check, 16 KB generated text, 256 KB upstream event stream, and a 60-second provider deadline (90-second route duration). Over-limit history is rejected rather than silently truncated. Subsequent replies can push stored history over the admission limit; start a new thread when the next send is refused. These limits are not a monthly spending cap. Provider error bodies and content are not logged or returned.

The browser keeps the desktop trail and transcript independently scrollable with a pinned composer; narrow screens switch between native Threads/Chat controls. Reload retains the selected conversation in the URL. Logout clears mounted client state, not server history. Navigating away does not finish a conversation; accepted work may already incur a provider charge.

## Approved-source practice

Apply `202603010007_practice_context.sql` after migration 006, without resetting data. Enable **Use approved sources** in a new or existing thread and ask for practice, an explanation or a hint. Keep it enabled to continue using current sources; reloading restores the last turn's mode. Turning it off preserves ordinary goals/organisation chat. The request mode is part of operation identity, so a persistence retry cannot quietly change the generation scope.

The service-only `server_practice_context` RPC validates the saved turn/account/Subject and atomically reads approved snapshots and records their document IDs, approved revisions and titles. Draft-only documents and Draft revisions are excluded. Each reply has an expandable **Approved sources selected** list; it records selected context, not a claim that every source informed the reply or that an incomplete request reached the provider. A later approval does not rewrite historical provenance. No complete source archive is stored in turns.

Selection is deliberately simple: the learner opts in to the current Subject's bounded approved collection; the model chooses relevant passages/documents for the learner's request. There is no embedding service, semantic index or hidden summarisation. More than 20 documents or 16,000 bytes of source JSON is refused in full, never silently truncated. Combined encoded history/source input is bounded to 36,000 bytes. Empty sources or oversized context leave an honest saved incomplete outcome without invoking the provider. Create/save a Learning Document, then choose **Ready to Practice**, to make material eligible. Existing user history remains saved on missing key/model or provider failures.

Instructions distinguish explanations/hints as assistance rather than independent performance, and approved/authored material as encountered rather than demonstrated understanding. Ordinary replies do not write Subject understanding or structured assessments; the separate recap workflow below owns reviewed interpretations. Prompt instructions reduce model misuse but are not a correctness guarantee: access boundaries are enforced by database selection and by the absence of tools, not by trusting model compliance.

## Reviewed Practice recaps

Apply `202603010008_reviewed_recaps.sql` after migration 007 using the Docker migration runner. In an existing conversation, choose **Request Practice recap**. A meaningful activity checkpoint can also produce an inline offer: the practice model emits a marker after a worked example, topic change or requested stopping point, not after a fixed number of messages. Offers do not invoke recap generation or block chat; the learner explicitly requests the potentially charged generation. This semantic offer depends on model judgement, not a calibrated assessment system.

`POST /api/recaps` accepts `{ subject, conversation, operation, action: 'generate' }`. The authenticated preparation RPC checks ownership and completed, approved-source practice since the last reviewed coverage checkpoint, captures a Subject-understanding revision and reserves a stable operation identity. Only the new activity is sent to the selected OpenAI model, with no document retrieval, profile or whole-history reprocessing. The 32,000-byte generation-input limit is enforced without truncation. The output must be a JSON object containing `text`, `difficulty`, `assistance` and `uncertainty`, each a nonblank string up to 1,200 UTF-8 bytes. Instructions demand concise interpretations, not quotations, subject-fact archives or mastery claims. A service-only completion RPC can update only the reserved pending proposal; deleted sources cannot be recreated by delayed output.

The proposal stays tentative until **Accept recap** or **Save corrected recap**. All four qualification fields can be edited. **Dismiss recap** changes neither earlier observations nor reviewed coverage. Chat remains available while a proposal is ignored, and generating another proposal never implicitly accepts the old one. Pending/interrupted generation does not retry automatically. Replaying its operation never invokes the provider again; a fresh explicit request may incur another charge.

Review uses `{ subject, operation, action: 'accepted' | 'corrected' | 'dismissed', observation? }`. The database serialises reviews against the current Subject-understanding revision and rejects stale/overlapping applications with HTTP 409. The browser keeps attempted corrections editable after rejection. Replaying a committed review cannot duplicate an observation. Accepted/corrected coverage advances only through the captured activity; newer messages remain tentative. Independent observations are appended, not replaced by later difficulty or success.

`GET /api/recaps?subject=<uuid>&conversation=<uuid>` returns scoped proposals, the reviewed checkpoint and this Subject's reviewed observations. **Reviewed observations** shows the outcome now, before the map slice. Active-session RLS protects all four new tables; authenticated callers cannot write tables or forge service completion. Approved Practice versions remain the only subject-material source; only reviewed observations are added to outgoing practice as provisional revisit context. Unreviewed/dismissed proposals are never retrieved for practice. The combined 36,000-byte practice input limit also includes reviewed observations; an oversized request is refused, not silently summarised.

Reviewed observations store only the bounded interpretation, qualification, activity range, source document IDs/titles/revisions and conversation provenance, not a hidden transcript or full-source copy. They have no proposal FK: deleting a conversation cascades proposals/checkpoints but sets the observation's conversation pointer to null while retaining its original identity. Document provenance uses identities rather than cascading FKs; the read boundary marks missing documents as deleted. Subject/account deletion still cascades observations. Later observation removal/reset must increment `subject_understanding.revision` and retain reviewed coverage to invalidate older proposals and prevent automatic rebuilding. Those user-facing mutations belong to ticket 13; deletion controls belong to tickets 14–16.

Verification: `tests/reviewed-recaps.spec.ts` covers controlled checkpoint offers, accept/correct/dismiss, continued conversation, incremental coverage, reload, reviewed-only outgoing context, stale applications with editable corrections, replay without duplicate observations/generation, foreign-account denial and direct-data write/service-RPC denial. Live-model interpretation quality still requires manual inspection.

## Adaptive chat assessments

Apply `202603010009_adaptive_assessments.sql` after migration 008. **Quick assessment** prepares an editable request in the existing composer and enables approved-source practice; **Send message** explicitly starts generation. In an unfinished activity the action becomes **Resume assessment**, preserving conversation/question identity. Natural-language requests containing assessment/assess, quiz, test me/my, or challenge me also enter the workflow with practice enabled. Topic requests are not constrained to a fixed list. Explicit easy/medium/hard constraints persist until changed; open difficulty may vary per question. A generated question at a different explicitly requested difficulty is refused rather than silently relabelled.

`chat_assessments`, `assessment_questions` and `assessment_responses` retain account-owned activity state, question identity/difficulty/status, and the turn IDs of answers, hints, explanations and skips. User text stays in the existing transcript. Active-session RLS permits owned reads only; the service-only finalisation RPC commits a completed readable reply and its activity changes together. It checks the saved source selection, owned pending turn and captured activity revision. Expired/deleted/stale work cannot create replacement history. The browser supplies `assessmentRevision` for existing activities, rejecting stale answers with text preserved. Stable operation identity includes this precondition; replay never generates twice.

Assessment output is bounded JSON streamed from the same provider request, buffered and validated server-side before publication. Unlike ordinary chat, partial structured JSON is not shown as a valid question or persisted as progress. Failures leave the saved learner message and an incomplete reply; no progress is advanced and retry is explicit. Completed turns expose an `assessment` snapshot through the existing conversation API and stream. The model sees only current approved material, reviewed observations, owned conversation context and current activity state; no separate syllabus retrieval or unreviewed-proposal retrieval exists.

The model returns one new question or none, feedback, topic, difficulty, learner-action classification and an optional semantic checkpoint. An open question cannot be silently replaced by hints/explanations/chat/resumption. **Hint**, **Explain question** and **Skip question** prepare ordinary editable chat requests without overwriting unsent text. Assistance is recorded against that question and labelled as non-independent performance. Skips are not assessed, never failed. Counters describe activity only; no mastery score or calibrated ability scale exists. Recap generation/review uses the existing inline workflow and explicit approval boundary. There is no hard three-question sequence or Finish ceremony.

Reload, Subject/thread switches, logout/login and another session reconstruct progress from saved turns. Unsent answers use the existing account/Subject/thread recovery mechanism, not a competing assessment draft store. Turning approved-source practice off permits ordinary chat without altering the assessment.

`tests/adaptive-assessments.spec.ts` exercises quick/natural-language entry, explicit difficulty changes, more than three questions, assistance and skip provenance, unsent recovery, cross-session resumption, qualified reviewed recaps, stale/replayed sends, failure honesty, approved-snapshot isolation and foreign/direct-data denial. Controlled wording is synthetic; live-model topic interpretation, action classification, teaching quality and question difficulty still need manual acceptance.

## Provider data handling and verification

History belongs to the app. Optional OpenAI stored-response retrieval is disabled, not all provider retention: abuse-monitoring logs may include content for up to 30 days, with policy exceptions. See the existing [provider research](../.scratch/production-release/research/free-email-and-openai.md) and [streaming guide](https://developers.openai.com/api/docs/guides/streaming-responses). Recheck terms before release.

Run `bash scripts/local.sh check` and `bash scripts/local.sh test` on the host; both execute Node tooling exclusively in Docker. `tests/conversations.spec.ts` exercises real Supabase Auth/persistence/RLS with the test-only outgoing OpenAI transport. No test endpoint or provider URL override is exposed by production code. Controlled streams do not prove live model teaching quality or real deployment compatibility; the real-key/phone release walkthrough remains required.
